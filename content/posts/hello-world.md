{{< note title="示例稿件" >}}
这是站点交付时的占位开场文。上线前请替换成你自己的版本：写清你是谁、正在学什么、为什么开始写，以及打算多久更新一次。
{{< /note >}}

## 写下来，是为了发现自己没懂

看书和听课时，"看懂了"是一种很便宜的感觉。真正检验理解的方式，是试着把一个知识点讲给一个没学过的人听——写博客就是这个过程的低成本版本。

一旦要落成文字，含糊的地方会立刻暴露：某个术语其实说不清边界，某两个步骤之间缺了一个前提，某段代码"照着敲能跑"但换一个输入就不知道为什么。这些缝隙在默读时会被大脑自动补上，写成文字就补不上了。

## 记录过程，而不只是结论

结论容易查到，过程很难。搜索能告诉你某个 API 怎么用，但不会告诉你：

- 第一次看文档时误读了哪句话；
- 报错信息里哪个词才是真正的线索；
- 试过哪两条弯路，以及为什么排除它们。

这些恰恰是几个月后重新遇到同类问题时最有用的东西。所以笔记里值得保留一张「我原本以为 → 实际是」的对照表，比只贴最终答案更有价值。

## 这个博客准备写什么

大致三个方向，都会围绕"学习过程"而不是"成果展示"：

| 方向 | 典型内容 | 触发时机 |
| --- | --- | --- |
| 编程实践 | 最小可运行示例、调试过程、工具链踩坑 | 写完一个能跑的小东西 |
| 论文与学术笔记 | 读三遍的笔记、目标函数拆解、复现记录 | 读完一篇并尝试复述 |
| 学习方法复盘 | 一段时间里哪些做法有效、哪些在自我感动 | 每月一次 |

## 更新节奏

先定一个不会失败的底线：**每周至少一篇，长短不限**。写不动的时候，把当天没搞懂的一个问题记成三五百字也算完成。稳定的低频，好过爆发式的三篇然后停更两个月。

{{< note title="给未来的自己" >}}
每篇文章结尾留一句"下次要验证什么"。下一篇的选题往往就藏在这里。
{{< /note >}}
